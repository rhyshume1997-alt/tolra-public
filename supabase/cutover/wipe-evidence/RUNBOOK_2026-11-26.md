## Steps 3 and 4 WITHOUT psql: two one-call files for the Supabase SQL editor (recommended for Rhys)
Files in this folder (generated by `build_single_call.py` from the unchanged script; each is ONE paste, ONE Run, role postgres):
- `RUN_1_DRYRUN_SINGLE_CALL.sql`: script + a wrapper. Returns ONE row `dry_run_result` = `{sqlstate P0001, message DRY_RUN_ROLLED_BACK, report {...}}`. Always rolls back: nothing is kept. Read the report against step 3 above. Any other message (a "wipe refused ..." text, a lock timeout 55P03) = stop.
- `RUN_2_REAL_SINGLE_CALL.sql`: first a PRECHECK block that aborts before anything is touched if: not running as postgres, organizations is not 3, a DATA_WIPE row already exists, a trigger is already disabled, or the FK/key inventory (521, `91d36c59...`) or trigger inventory (485, `9f4cb4c6...`) differs from the reviewed production schema; then the script; then the real call with the approved counts. One Run = one transaction: **if any check inside fails, the whole call errors and NOTHING is committed; it commits only when every check passed**, and the single result row `wipe_report` is the full report. Run it ONLY after Rhys says GO following RUN 1. The only pause is between RUN 1 and RUN 2.
Safe sequence: (a) preflight 1 and 2 as SELECTs (editor or Claude), (b) paste RUN 1, read the row, (c) Rhys says GO, (d) paste RUN 2, (e) read `wipe_report` (dry_run false, users_deleted 3, counters_previous), (f) post-commit checks (step 5), (g) Storage (step 6).
Notes: the editor may show a "destructive query" confirmation: that is expected for RUN 2 only. If the editor times out or the browser closes mid-run, the database finishes or rolls back the single statement by itself: check with step 5 queries (organizations still 3 and DATA_WIPE 0 means nothing happened). Do not click Run twice: a second RUN 2 refuses itself (PRECHECK: organizations <> 3).
