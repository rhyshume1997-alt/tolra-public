# Fake transfer rehearsal data

BB generates exports for **Example alpha Engineering** and **Example beta Engineering**. No real company data is used. Default per company: 300 customers, 300 suppliers, 300 open jobs, 300 linked POs, 300 invoices and 200 payments. Each company has 100 paid, 100 part-paid and 100 unpaid invoices. Dates are fixed around the 12 November 2026 rehearsal. All money starts as integer pennies; VAT is exactly 20%. Names say Example and email addresses use example.test.

1. From this branch, create a new folder. This writes CSV/JSON files only. There is no database connection, SQL, network request or write mode. An existing folder is refused to protect any real exports.

   ```bash
   node scripts/mock-production/generate.mjs --out /tmp/tolra-fake-transfer --count 300
   ```

2. Run the existing offline importer for each fake company. These commands create reports only and write nothing to any database. They do not create companies or load records. No database URL, credentials, --write or --install-importer is supplied.

   ```bash
   node scripts/sliq-import/cli.mjs /tmp/tolra-fake-transfer/alpha --mapping synthetic --out /tmp/tolra-fake-alpha-report
   node scripts/sliq-import/cli.mjs /tmp/tolra-fake-transfer/beta --mapping synthetic --out /tmp/tolra-fake-beta-report
   ```

3. Compare each report.json and report.md to expected-reconciliation.json. Counts, net, VAT, gross, payments, outstanding balance and PO total must agree exactly in pennies. There must be no held invoices, amount mismatches or ambiguous customer links. All 300 jobs and 300 PO links must be planned. Use jobs-verification.csv for the job/PO cross-check. Empty sales-order/WIP/credit-note files intentionally have headers: those optional records are not generated by this fixture.

4. A database rehearsal is a separate operator action. On the approved disposable stack, create two new fake companies using the existing fixture/company creation flow. Record their actual IDs. Use this branch's existing SliQ CLI read-only target check and guarded write process for each separate folder/ID after its release prerequisites and report are reviewed. Never reuse the placeholder IDs from unit tests as real company IDs. Never point the writer at JNR, Marpet or a hosted/live database. This generator adds no alternate importer or bypass.

5. After the authorised load, compare actual database counts/money/job links with each company's expected report, then repeat the import: no new rows, changed balances or changed document numbers are allowed. Take both companies' snapshots before importing either one, and prove the other company's rows remain unchanged. Identical source account/document numbers across folders deliberately exercise company isolation. Stable planned IDs are tested here; real write idempotence/RLS is NOT proved without that separate database run.

Validation: tests/unit/mock-production-generator.test.ts uses the real importer dry run for 600 invoices, compares independent counts/totals and repeat plans, rejects every attempted network/database connection, and checks cross-company IDs, deterministic files, overwrite refusal, size guards and unsupported write/input flags. No generated CSV data is committed. No SQL or database seed was executed.
